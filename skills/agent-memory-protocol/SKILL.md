# Persistent Agent Memory Protocol

당신의 서브에이전트 이름 기준으로 `.claude/agent-memory/<서브에이전트명>/`(현재 작업 중인 프로젝트 저장소 루트 기준)에 영속적인 파일 기반 메모리 시스템이 있습니다. 프로젝트마다 완전히 독립적으로 저장되며 **절대 프로젝트 간 메모리를 섞지 않습니다.** 이 디렉토리는 각 프로젝트에 이미 존재하므로 mkdir이나 존재 확인 없이 바로 Write 툴로 씁니다.

시간이 지나며 이 메모리 시스템을 계속 쌓아가서, 향후 작업에서 사용자가 누구인지, 어떻게 협업하고 싶어하는지, 어떤 행동을 피하거나 반복해야 하는지, 그리고 작업 배경 맥락을 온전히 파악할 수 있도록 합니다.

사용자가 명시적으로 기억해달라고 요청하면 가장 적합한 타입으로 즉시 저장합니다. 잊어달라고 요청하면 관련 항목을 찾아 제거합니다.

## 메모리 타입

저장할 수 있는 별개의 메모리 타입은 다음과 같습니다:

<types>
<type>
    <name>user</name>
    <description>사용자의 역할, 목표, 책임, 지식에 대한 정보. 좋은 user 메모리는 사용자의 선호/관점에 맞춰 향후 행동을 조정하는 데 도움이 됩니다. 사용자에 대한 부정적 판단으로 보일 수 있거나 작업과 무관한 내용은 피합니다.</description>
    <when_to_save>사용자의 역할, 선호, 책임, 지식에 대한 세부사항을 알게 될 때</when_to_save>
    <how_to_use>사용자의 프로필/관점을 반영해야 하는 작업을 할 때</how_to_use>
</type>
<type>
    <name>feedback</name>
    <description>작업 접근 방식에 대해 사용자가 준 지침 — 피해야 할 것과 계속해야 할 것 모두. 실패와 성공 양쪽에서 기록합니다: 교정만 기록하면 과거 실수는 피하지만 이미 검증된 접근에서 멀어지고 지나치게 조심스러워질 수 있습니다.</description>
    <when_to_save>사용자가 접근 방식을 교정할 때("아니 그거 말고", "하지 마") 또는 비직관적인 접근이 성공했음을 확인해줄 때("맞아 그거야", "계속 그렇게 해줘", 특이한 선택을 이의 없이 받아들일 때). 교정은 눈에 띄지만 확인은 조용히 지나가기 쉬우니 주의 깊게 관찰합니다. *왜* 그런지 포함해서 저장해야 나중에 엣지 케이스를 판단할 수 있습니다.</when_to_save>
    <how_to_use>이 메모리가 행동을 안내하게 하여 사용자가 같은 지침을 두 번 줄 필요가 없게 합니다.</how_to_use>
    <body_structure>규칙 자체를 먼저 쓰고, `**Why:**` 줄(사용자가 준 이유 — 과거 사고나 강한 선호)과 `**How to apply:**` 줄(이 지침이 언제/어디에 적용되는지)을 씁니다.</body_structure>
</type>
<type>
    <name>project</name>
    <description>코드나 git 히스토리로는 알 수 없는, 진행 중인 작업/목표/이니셔티브/버그/사고에 대한 정보. 사용자가 하는 작업의 더 넓은 맥락과 동기를 이해하는 데 도움이 됩니다.</description>
    <when_to_save>누가 무엇을 왜, 언제까지 하는지 알게 될 때. 이런 상태는 빠르게 변하므로 최신으로 유지합니다. 사용자 메시지의 상대적 날짜는 절대 날짜로 변환해서 저장합니다(예: "목요일" → "2026-03-05").</when_to_save>
    <how_to_use>사용자 요청의 세부사항과 뉘앙스를 더 온전히 이해하고 더 나은 제안을 하는 데 사용합니다.</how_to_use>
    <body_structure>사실/결정을 먼저 쓰고, `**Why:**` 줄(동기 — 제약, 마감, 이해관계자 요청)과 `**How to apply:**` 줄(이것이 제안에 어떻게 영향을 주는지)을 씁니다. project 메모리는 빠르게 낡으므로 Why가 향후 유효성 판단에 도움이 됩니다.</body_structure>
</type>
<type>
    <name>reference</name>
    <description>외부 시스템에서 정보를 찾을 수 있는 위치에 대한 포인터. 프로젝트 디렉토리 밖의 최신 정보를 어디서 찾을지 기억하게 해줍니다.</description>
    <when_to_save>외부 시스템의 리소스와 그 용도를 알게 될 때(예: 버그는 Linear 특정 프로젝트에서 추적, 특정 Slack 채널에서 피드백을 찾을 수 있음).</when_to_save>
    <how_to_use>사용자가 외부 시스템이나 그곳에 있을 수 있는 정보를 언급할 때</how_to_use>
</type>
</types>

## 메모리에 저장하지 말아야 할 것

이 메모리의 목적은 매번 코드를 다시 탐색하지 않게 하는 것이므로, 각 에이전트 본문의 메모리 지침이
지정한 항목(프레임워크/DB/datasource 구성, 소스·웹 경로 구조, 모듈별 구현·컨벤션 패턴, 공통 유틸 위치,
반복되는 실수와 해결책, 반복 취약점 패턴 등)은 저장합니다. 다음은 저장하지 않습니다:

- git 히스토리, 누가 무엇을 바꿨는지 — `git log`/`git blame`이 정답입니다
- CLAUDE.md 파일에 이미 문서화된 내용
- 일시적인 작업 세부사항: 진행 중인 작업, 임시 상태 — `TASK_STATUS.md`에 남깁니다
- 권한 우회 수단

사용자가 명시적으로 저장을 요청해도 이 제외 규칙은 그대로 적용합니다. PR 목록이나 활동 요약 저장을 지시받으면, 그중 *놀라웠거나 비직관적인* 부분만 골라 저장합니다 — 그게 보존할 가치가 있는 부분입니다. 무엇이 그에 해당하는지 판단할 수 없으면 저장하지 말고, 그 사실을 결과 보고에 적어 메인 세션이 판단하게 합니다.

## 메모리 저장 방법

메모리 저장은 2단계 프로세스입니다:

**1단계** — 아래 frontmatter 형식으로 메모리를 자기 파일(예: `user_role.md`, `feedback_testing.md`)에 씁니다:

```markdown
---
name: {{short-kebab-case-slug}}
description: {{한 줄 요약 — 향후 대화에서 관련성 판단에 쓰이므로 구체적으로}}
metadata:
  type: {{user, feedback, project, reference}}
---

{{메모리 내용 — feedback/project 타입은 사실/규칙 → **Why:** → **How to apply:** 구조로. 관련 메모리는 [[다른-메모리-name]]으로 링크}}
```

본문에서 `[[name]]`으로 다른 메모리와 링크합니다. 아직 존재하지 않는 `[[name]]`도 괜찮습니다 — 나중에 써야 할 것을 표시하는 것이지 오류가 아닙니다.

**2단계** — `MEMORY.md`에 그 파일에 대한 포인터를 추가합니다. `MEMORY.md`는 인덱스이지 메모리 자체가 아닙니다 — 각 항목은 한 줄, 150자 이내: `- [제목](file.md) — 한 줄 요약`. frontmatter는 없습니다. 메모리 내용을 `MEMORY.md`에 직접 쓰지 않습니다.

- `MEMORY.md`는 항상 대화 맥락에 로드됩니다 — 200줄 이후는 잘리므로 인덱스를 간결하게 유지합니다
- 메모리 파일의 name/description/type 필드를 내용과 최신으로 맞춥니다
- 시간순이 아니라 주제별로 의미론적으로 정리합니다
- 틀렸거나 낡은 메모리는 갱신하거나 제거합니다
- 중복 메모리를 쓰지 않습니다. 새로 쓰기 전에 업데이트할 기존 메모리가 있는지 먼저 확인합니다

## 메모리 접근 시점
- 메모리가 관련 있어 보이거나, 사용자가 이전 대화의 작업을 언급할 때
- 사용자가 명시적으로 확인/기억/회상을 요청하면 반드시 메모리에 접근합니다
- 사용자가 메모리를 *무시*하거나 *쓰지 말라*고 하면: 기억된 사실을 적용, 인용, 비교, 언급하지 않습니다
- 메모리 기록은 시간이 지나며 낡을 수 있습니다. 메모리를 특정 시점에 참이었던 맥락으로 사용하세요. 메모리 기록만 근거로 사용자에게 답하거나 가정을 세우기 전에, 파일/리소스의 현재 상태를 읽어 그 메모리가 여전히 맞는지 확인합니다. 회상한 메모리가 현재 관측한 정보와 충돌하면 지금 관측한 것을 신뢰하고, 낡은 메모리를 그대로 따르는 대신 갱신하거나 제거합니다

## 메모리 추천 전 확인사항

특정 함수, 파일, 플래그를 지칭하는 메모리는 *그 메모리가 작성된 시점에* 그것이 존재했다는 주장입니다. 이름이 바뀌었거나, 제거됐거나, 애초에 병합되지 않았을 수 있습니다. 추천하기 전에:

- 메모리가 파일 경로를 지칭하면: 그 파일이 존재하는지 확인
- 메모리가 함수나 플래그를 지칭하면: grep으로 확인
- 사용자가 그 추천에 따라 행동하려 한다면(단순히 히스토리를 묻는 게 아니라): 먼저 검증

"메모리에 X가 있다고 적혀 있다"는 "지금 X가 존재한다"와 같지 않습니다.

저장소 상태를 요약하는 메모리(활동 로그, 아키텍처 스냅샷)는 그 시점에 고정된 것입니다. 사용자가 *최근* 또는 *현재* 상태를 물으면, 스냅샷을 회상하기보다 `git log`나 코드를 직접 읽는 것을 우선합니다.

## 메모리와 다른 형태의 영속성

메모리는 현재 작업을 돕는 여러 영속화 메커니즘 중 하나입니다. 미래 대화에서 회상 가능한 것과, 현재 대화 범위에서만 유용한 것을 구분합니다. 진행 중인 작업 절차나 임시 상태는 메모리가 아니라 `TASK_STATUS.md`(A/B/C/D 공유 작업 로그) 등 현재 작업에 특화된 메커니즘에 남깁니다.

- 이 메모리는 project 범위이므로 메모리 내용을 이 프로젝트에 맞게 작성합니다. 프로젝트에 따라 `.claude/`가 git에서 제외되어 로컬에만 남을 수 있으므로, 팀과 공유된다고 가정하지 않습니다
